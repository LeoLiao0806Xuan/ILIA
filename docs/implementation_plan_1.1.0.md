# ILIA 1.1.0 可执行架构与实施计划

> 版本主题：**ILIA 1.1 — Offline Legal Research Workspace / ILIA 1.1——离线国际法研究工作台**

本文把 1.1.0 产品设想转换为工程实施基线。它规定目标边界、模块职责、数据与接口契约、依赖顺序、里程碑、任务和发布门槛。任务完成状态以代码、自动化测试和版本化验收证据为准，而不是以界面可见为准。

## 1. 目标与边界

1.1.0 的单一产品目标是：把“能离线问国际法”升级为“可以完成国际法研究工作流的桌面助手”。核心资料仍限于国际法；新增能力围绕检索、可核验回答、资料阅读、个人资料、研究整理和离线更新展开。

### 1.1 必须交付

- 快速查询、标准问答、深度研究三种互相独立的问答模式；运行模式不得与 CUDA/Vulkan/CPU 后端绑定。
- 回答流式输出、请求取消、新请求替换旧请求以及异常后的进程清理。
- 原文、中文机器译文和中英对照阅读；正式引用始终以原文为准。
- 引证逐项检查、无证据拒答和点击引证定位证据。
- 资料类型、主题、资料库和指定文书过滤，并在检索层强制执行。
- 项目、收藏、笔记、会话历史，以及 Markdown、HTML 研究备忘录导出。
- PDF、TXT、Markdown、HTML、DOCX 个人资料导入；预览确认、哈希去重、删除和重建向量。
- 核心库、个人资料库、研究工作区三库隔离。
- 本地手动更新包、网络错误分类和本机代理设置。
- 每次发布生成独立的数据库验证报告，并在构建时执行资料许可门禁。

### 1.2 条件交付

- OSCOLA、Bluebook、ICJ、Markdown 脚注和纯文本引用复制。
- 基于人工维护或可验证元数据的“相关资料”。
- 可选、可独立下载的轻量 reranker。
- 模型空闲释放显存和 HTTP Range 断点续传。

这些项目不得阻塞必须范围发布；只有在对应里程碑没有未关闭的 P0/P1 缺陷时才进入 1.1.0。

### 1.3 明确不进入 1.1.0

中国法完整资料包、合同审查、OCR、复杂知识图谱、云同步、账号系统、多人协作、7B 或更大模型、模型微调、移动端、macOS 和 Linux 安装包。

## 2. 架构原则

1. **离线优先**：除用户主动检查更新、打开官方来源或下载可选模型外，研究流程不产生网络请求。
2. **证据优先**：生成是证据的下游；检索过滤、证据编号和引证定位必须由程序控制，不交给提示词决定。
3. **三库隔离**：随包核心数据只读，用户资料和工作区分别可写；核心更新不能修改后两者。
4. **有界编排**：深度研究最多 3—5 个子问题、每个子问题一次检索，不做无限 Agent 循环。
5. **可恢复写入**：导入、删除、重建索引、更新和迁移均使用事务、临时文件或可回滚日志。
6. **稳定标识**：引用、收藏和笔记使用资料库命名空间加稳定 ID，不依赖结果排名。
7. **渐进增强**：无 Qwen、无 reranker、无网络时，快速查询和本地资料阅读仍完整可用。
8. **发布证据版本化**：验证报告、评测报告、权利矩阵和安装验收记录都必须包含版本，不允许静默复用旧报告。

### 3.1 现有 crate 的演进

| 模块 | 1.1.0 职责 |
|---|---|
| `ilia-core` | 放置稳定的请求/响应、过滤器、资料库命名空间、流事件、引证检查和导入状态类型。不得依赖 Tauri。 |
| `ilia-database` | 保留核心库只读访问；增加带过滤条件的查询构造器和用户库写入接口。所有 SQL 过滤在这里完成。 |

| `ilia-updater` | 增加本地更新包、错误分类、代理和可选断点续传；继续负责签名、哈希、路径安全和回滚。 |

## 4. 数据架构

### 4.1 文件位置与生命周期

| 数据库 | 位置 | 权限 | 更新策略 |
|---|---|---|---|
| `core.sqlite` | 安装资源目录 | 只读 | 仅由已签名核心资料更新替换或迁移 |
| `user.sqlite` | Tauri 应用数据目录 | 读写 | 只由用户导入、删除或重建；应用更新不得覆盖 |
| `workspace.sqlite` | Tauri 应用数据目录 | 读写 | 只由研究操作修改；应用更新只运行前向迁移 |

源码树中的 `data/ilia.sqlite3` 在过渡期仍作为核心库构建产物；打包阶段映射为 `core.sqlite`。完成迁移前不得直接重命名发布资产，以免破坏 1.0.x 更新路径。

### 4.2 统一 ID

跨库引用统一使用：

```text
core:<document_id>:<chunk_id>
user:<document_uuid>:<chunk_uuid>
```

所有回答引证、收藏、笔记和导出保存该稳定键。排名 `【n】` 只是一次回答内的显示编号。删除个人资料前应向用户报告关联收藏/笔记数量；研究记录保留标题、引文和文本快照，并标记来源已删除。

### 4.3 `user.sqlite` 最小 schema

- `user_documents`：UUID、标题、语言、资料类型、来源文件名、SHA-256、字节数、导入状态、创建时间。
- `user_document_aliases`：简称和别名。
- `user_chunks`：稳定 UUID、文书 UUID、顺序、定位标签、原文、规范化文本、语言。
- `user_chunks_fts`：FTS5 索引。
- `user_embeddings`：模型 ID、维度、向量、范数。
- `import_jobs`：阶段、进度、错误、临时路径和可恢复状态。
- `schema_migrations`：数据库 schema 版本。

用户库与核心库不建立 SQLite 跨文件外键。联合结果在 Rust 层合并，避免核心库替换时破坏用户数据。

### 4.4 `workspace.sqlite` 最小 schema

- `projects`、`project_tags`、`tags`；
- `conversations`、`messages`、`message_citations`；
- `saved_evidence`：稳定来源键、标题、引用、原文快照、来源状态；
- `notes`：可关联项目、消息或证据；
- `memo_sections`：研究备忘录的有序段落；
- `schema_migrations`。

所有可写表使用 UUID 和 UTC 时间。删除采用明确的级联规则；数据库开启 `foreign_keys=ON`、WAL 和合理的 busy timeout。导出只读取一致性事务快照。

## 5. 核心接口契约

### 5.1 检索

```rust
pub enum ResearchMode { Quick, Standard, Deep }
pub enum LibraryScope { All, CoreOnly, UserOnly }

pub struct SearchFilters {
    pub library: LibraryScope,
    pub document_types: Vec<DocumentType>,
    pub topic_ids: Vec<String>,
    pub document_keys: Vec<String>,
}

pub struct SearchRequest {
    pub query: String,
    pub filters: SearchFilters,
    pub limit: usize,
    pub evidence_limit: usize,
}
```

`SearchHit` 增加 `library_kind`、`stable_key`、可选主题和结构化案件/条约元数据。过滤条件必须传到精确、FTS5 和向量三条查询路径；测试必须证明被排除资料不会出现在候选集，而不只是最终 UI。

排序顺序为：精确条/段命中、文书名/年份命中、FTS5、向量。融合后执行同文书配额、重复压缩和相邻内容合并。当前 5,093 条核心数据加个人资料的目标规模不足 20,000—50,000 chunks 时继续顺序向量扫描，不引入 HNSW。

### 5.2 研究请求与流事件

```rust
pub struct ResearchRequest {
    pub request_id: Uuid,
    pub question: String,
    pub mode: ResearchMode,
    pub answer_language: AnswerLanguage,
    pub filters: SearchFilters,
}

pub enum ResearchEvent {
    Started,
    RetrievalCompleted { evidence_count: usize },
    PlanReady { subquestions: Vec<String> },
    AnswerDelta { text: String },
    CitationAuditCompleted { findings: Vec<CitationFinding> },
    Completed { response: AnswerResponse },
    Cancelled,
    Failed { code: String, safe_message: String },
}
```

快速查询只发送检索事件，不启动 llama-server。标准问答使用最多 5 条证据。深度研究先产生 3—5 个可见子问题，逐个检索，按稳定键去重，再在证据预算内生成固定六段结构。每个前端窗口同一时间只允许一个活动研究请求；新请求先取消旧请求。

### 5.3 引证检查

引证检查分为两层：

1. 确定性检查：编号存在、稳定键可解析、每个实质性陈述包含引证、引用证据属于本次证据包。
2. 语义支持检查：将陈述和对应证据交给本地模型，以受约束 JSON 返回 `direct`、`summary`、`unsupported` 或 `conflict`，解析失败按 `unsupported` 处理。

`direct` 显示绿色，`summary` 显示黄色，后两类显示红色并触发一次受约束重写；重写后仍为红色的陈述从最终回答删除，并加入“部分结论因缺少证据未输出”。语义标签是 ILIA 的自动核验结果，不应表述为法律真实性证明。发布前用人工标注样本测量误判。

### 5.4 导入

导入是两阶段协议：

1. `prepare_import(path)`：检查文件类型、大小、SHA-256 和重复项，提取文本到受控临时目录，返回只读预览和推断元数据。
2. `commit_import(preview_id, confirmed_metadata)`：切分、嵌入并在单一数据库事务中写入文书、FTS 和向量；成功后删除临时文件。

支持扩展名并验证实际内容：PDF（文本层）、TXT、Markdown、HTML、DOCX。扫描 PDF 明确返回“当前版本不支持 OCR”，不得导入空文本。HTML 删除脚本和样式；DOCX 只读取正文、标题、列表和表格文本，不执行宏或外部关系。路径和原文件内容不进入日志。

### 5.5 更新

`.ilia` 是带版本的容器，不只是改扩展名的任意文件。建议结构：

```text
package.json              # 格式版本、release_id、目标版本、负载清单
update-manifest.json      # 与在线更新共用的规范清单
update-manifest.sig       # Ed25519 分离签名
payloads/*.payload
```

导入本地包时先在临时目录限制性解包，拒绝绝对路径、`..`、重解析点、重复条目和超出声明大小的内容，再复用现有 `verify_manifest`、SHA-256、`UpdateEngine::apply` 和回滚路径。在线错误映射为稳定代码：`dns_failed`、`connect_timeout`、`server_unreachable`、`download_interrupted`、`invalid_signature`、`invalid_payload`、`up_to_date`。

代理配置存放于本机应用配置目录，日志必须脱敏用户名、密码和 URI。离线研究命令不得读取或使用代理。

## 6. UI 信息架构

主导航固定为四区：研究、项目、资料库、设置。

- **研究**：模式切换、问题、回答语言、资料过滤器、流式回答、停止按钮、证据列表和双语阅读器。
- **项目**：项目/标签、会话、收藏、笔记、备忘录编排和导出。
- **资料库**：核心与个人资料明确分组；导入预览、重复提示、删除和重建状态。
- **设置**：GPU、显存、后端、上下文、GPU 层、估算内存、性能档位、代理和更新诊断。

证据阅读器提供“原文 / 中文 / 对照”三态。对照模式必须同时保留原文和“ILIA 机器翻译，非官方译文”标识；复制引文默认使用原文。引证按钮使用稳定证据键定位并滚动，不以数组下标之外的隐式状态关联。

## 7. 里程碑与依赖顺序

### M0：发布与架构基线

目标：清除 1.0.1 已知审计歧义，为后续数据库变更建立门禁。

退出条件：生成带版本的 1.0.1 验证报告；构建拒绝 `red`、`pending` 和不满足处理条件的 `yellow` 资料；三库 schema、稳定 ID 和研究事件契约经测试固定。

### M1：三库隔离与范围检索

目标：先建立所有后续功能依赖的数据边界。

退出条件：核心库只读、空用户库和工作区自动创建/迁移；核心/用户联合检索可工作；所有过滤器在精确、FTS 和向量路径生效；现有 197 题无回归。

### M2：三种模式、流式生成与引证审计

目标：完成 1.1.0 的研究主链路。

退出条件：快速查询不启动模型；标准问答流式返回且可在 2 秒内停止；深度研究有界运行；红色陈述按规则重写或删除；引证点击稳定定位。

### M3：本地研究工作区

目标：让检索结果可积累为研究成果。

退出条件：项目、标签、会话、收藏和笔记完整持久化；重启后恢复；可组合并导出确定性的 Markdown 与自包含 HTML；删除来源后快照仍可读并标记状态。

### M4：受控个人资料导入

目标：交付不带 OCR 的个人资料库。

退出条件：五种格式完成预览确认、去重、切分、嵌入和检索；取消/失败不留下半成品；删除后 FTS 和向量无残留；核心更新不影响用户库；导入全程无网络请求。

### M5：更新、诊断与性能体验

目标：补全受限网络和不同硬件下的可维护性。

退出条件：本地 `.ilia` 包签名验证、安装、失败回滚通过；在线错误给出用户可理解分类；代理秘密不入日志；预热、状态展示和性能档位完成。断点续传与空闲释放显存视稳定性决定是否进入 1.1.0。

### M6：发布硬化与验收

目标：只做缺陷收敛、证据生成和发布，不再增加产品范围。

退出条件：全部发布门槛通过；安装、升级、中断回滚、卸载、离线和隐私测试形成版本化证据；文档、NOTICE、安装介质和 Release 资产一致。

## 9. 发布门槛

### 9.1 检索

- 至少 300 题；Recall@5 ≥ 0.98。
- 精确条款定位正确率 100%。
- 中英文文书名识别正确率 ≥ 99%。
- 每一种过滤器都有负向用例，过滤范围外命中为 0。
- 现有 197 题基线不得低于 1.0.1 指标；若题目或语料变化，报告必须同时给出可比子集。

### 9.2 问答与引证

- 有实质性结论但无引用的最终回答比例为 0。
- 不存在或越界的引用编号比例为 0。
- 明确无证据问题拒答率 100%。
- 引证点击定位正确率 100%。
- 语义支持检查另行报告人工标注集上的 precision/recall；在指标固定前不得宣称其能证明法律结论正确。

### 9.3 性能与生命周期

- 发布目标机上纯检索 p95 ≤ 2 秒；报告硬件、冷热缓存和样本数。
- 已加载模型后尽快显示首段，并记录 p50/p95 首段延迟，不用模糊主观描述替代。
- 点击停止后 ≤ 2 秒终止输出，连续 20 次取消无孤儿进程。
- CUDA 失败可自动降级到 Vulkan 或 CPU，并显示具体原因。

### 9.4 用户资料和工作区

- 重复文件可识别；删除后文书、FTS、向量全部清除。
- 导入失败或取消不留下可检索的半成品。
- 核心数据库更新前后 `user.sqlite` 与 `workspace.sqlite` 内容不丢失。
- 用户文件的导入、嵌入、检索和导出不产生网络请求。
- Markdown 与 HTML 导出通过快照测试和活动内容安全测试。

### 9.5 更新与合规

- GitHub 不可访问不影响启动和离线研究。
- 本地更新完成签名、哈希、版本、路径、数据库完整性和回滚验证。
- 更新中断后旧版本仍可启动。
- 发布包中 `red`、`pending` 资料和来源 PDF 为 0；每项 `yellow` 均有满足条件的机器可验证证据。
- `validation_report_<version>.json` 中的资料、chunk、向量和 FTS 数与待发布数据库实时一致。

## 11. 风险与决策点

| 风险 | 处理 |
|---|---|
| 4B 模型对“引证是否支持陈述”的判断不稳定 | 确定性检查先行、语义失败关闭、只重试一次、红色删除、人工标注集测量。 |
| PDF/DOCX 提取扩大攻击面 | 严格文件/大小限制、无宏无外链、隔离临时目录、恶意 fixture；OCR 延后。 |
| 三库联合查询造成延迟 | 并行查询后在 Rust 层融合；先测量，达到规模阈值再评估 HNSW。 |
| 深度研究上下文超限 | 子问题上限、同文书配额、全局证据预算和确定性去重。 |
| 更新包可成为任意文件写入入口 | 继续复用相对路径、重解析点、签名和哈希门禁；限制性解包并加入攻击测试。 |
| 用户数据迁移失败 | 更新前备份、事务迁移、只前向迁移、失败保留原库并进入只读恢复提示。 |
| `yellow` 资料的全球分发风险仍存在 | 构建门禁只能执行既定产品方条件，不能替代书面许可或司法辖区法律意见；状态不得标为 `green`。 |

## 12. 执行规则

- 按 M0 → M6 顺序推进；M1 未稳定前不合并依赖个人库的 UI，M2 未稳定前不扩展深度研究格式。
- 每个任务的 PR 必须包含测试、用户可见错误、数据迁移影响和文档更新；涉及数据库或更新的 PR 还必须包含失败/回滚用例。
- 里程碑退出时冻结对应接口。后续破坏性变更必须附迁移方案并重跑此前所有门槛。
- M6 开始后只接受 P0/P1 缺陷修复、报告再生成和发布工程修改；P2 自动移入 1.1.x。
- 1.1.0 的版本号只在 M6 发布候选切换，开发阶段使用 `1.1.0-dev`，避免未完成构建被误认为正式发布。
